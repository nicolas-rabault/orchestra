# P4 — The monitoring page, the allocated port, and the machine's own listing

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `orchestra monitor` serves a page that shows what this project's orchestra is doing and
lets a human answer a worker's question from a browser — on a port allocated so four projects can
each have one, with each page naming the project it is piloting. And `orchestra instances`, which
says which page is which.

**Architecture:** The same split every subsystem here keeps. `lib/monitor/sources.mjs` is the only
module that touches the filesystem, git or a child process; `model.mjs`, `layout.mjs`, `tabs.mjs`,
`progress.mjs`, `answers.mjs`, `clock.mjs` and `keys.mjs` are pure, which is what lets them be
tested without a repository and served to the browser unchanged, so the page and the suite count
the same way. `server.mjs` routes and decides nothing. `lib/monitor/port.mjs` owns the one rule for
which port a project gets. `lib/cli/monitor.mjs` wires two subcommands.

**Tech Stack:** ESM, node builtins only (`node:http`, `node:child_process`, `node:fs`, `node:path`,
`node:url`, `node:crypto`), `node:test` + `node:assert/strict`. No runtime dependencies. The
browser half is plain ES modules with no bundler and no framework.

**Spec:** `docs/specs/2026-09-02-orchestra-plugin-design.md` — **§7** is this phase (the monitor,
and the two additions it requires), with **§8.1** (the project's `name` and derived `id`), **§8.2**
(`~/.orchestra/instances.json`, already written by `lib/machine.mjs`), **§8.3** (port allocation:
the deterministic candidate, the upward probe, recording the port actually bound, and a pinned port
in conflict being a `doctor` error), §3.1 (`monitor.port`, `worktrees`, `name`), §3.2 (runtime
state resolves to the main checkout), §8.4 (worker session names), §14 (two fixtures and a
temporary `HOME`) and §15, whose P4 row is the acceptance.

**Port source:** `~/Projects/planetCraft/tools/orchestra/monitor/` (13 modules and `public/`, 1735
+ 1528 lines) and `tests/orchestraMonitor.test.js` (1719 lines, 173 tests), at `86bf8412`, the
commit the README records the extraction from. **Never write anything under
`~/Projects/planetCraft`** — it is the source, not a workspace.

**Repository state at planning time:** `main` at `eff5a90` (`refactor(store): delete setStatus and
close, which sync replaced`), 316 tests green, no remote, plugin installed at 0.4.0.

## The scope questions, answered

These were put to this plan explicitly. Each answer is binding; **an implementer who thinks one is
wrong should say so in their report rather than quietly do the other thing** — five times in P2b an
implementer found the brief wrong and was right to override it, and that is worth more than
obedience. What is not allowed is doing the other thing silently.

### 1. The page is the inbox's first writer, and the writer lives beside the reader

`lib/register/inbox.mjs` opens with "the monitor appends, orchestra reads", and until now only the
reading half existed: `orchestra inbox` prints nothing because nothing writes `.orchestra/inbox.jsonl`.
That file is the promise of this phase.

`appendAnswer(path, entry)` goes into **`lib/register/inbox.mjs`**, not into the monitor. One module
defines the channel — its shape, its timestamp precision and its `from` marker — so the writer and
the reader cannot drift. Write against `unconsumed`, which already ships, and not against a fresh
idea of what an answer is:

- the entry is `{ ts, task, pending, answer, from: 'monitor' }` and **nothing else**. `model.mjs`
  rejects an inbox line that is not `from: 'monitor'`, because the monitor is that file's only
  writer and a conductor's own journal line landing there was once rendered as the user's words;
- `ts` is `new Date().toISOString()` at **full millisecond precision**. Truncated to the second, a
  remark written in the same second as `conductor.inboxSeen` is indistinguishable from the stamp
  and `after()` drops it;
- `pending` is the id from `pendingId(reg.id, item)` — `lib/register/pending.mjs`'s, the one the
  register already computes — or `null` for a free remark that targets no item;
- append only. Never rewrite, never truncate; a crash mid-write costs one skipped line and
  `readJsonl` already counts it.

The four-hour grace (`PENDING_GRACE_MS`), the shared `inboxSeen` cursor and the stolen-stamp rule
are the reader's and are already tested. **Do not re-derive them and do not add a second copy in
the page.** What the page owns is its own client-side mirror of one of them — see `answers.mjs` in
Task 3 — and that mirror's whole argument is that it is a mirror.

### 2. `lsof` for liveness; a real `bind` for allocation; `curl` never

Two different questions, two different tools, and conflating them is how this cost a conductor:

- **"Is a page there?"** — `lsof` on the port read from the registry. Measured 2026-08-12 in
  planetCraft: `curl` from the conductor's shell could not reach a localhost server that `lsof`
  proved was listening and a browser was using, so the `curl` form hung for ever and the `||`
  never fired. `curl` appears nowhere in this phase, in code, in a test or in a document.
- **"Is this port free?"** — bind it. Nothing else is authoritative, and `lsof` is not: it answers
  about listeners it can see, and losing a race between the answer and the bind is exactly the
  failure allocation must not have. So the probe **is** the bind, on the one `http.Server` that
  will keep it: `server.listen(port, '127.0.0.1')`, catch `EADDRINUSE` on the server's `error`
  event, `server.listen(port + 1)`, and so on. **Never bind a throwaway socket to test a port and
  then close it before the real listen** — that is a window another process takes.

### 3. Port allocation, exactly

`monitor.port` is `"auto"` (the default) or an integer, and `lib/config.mjs` already validates that.

- **`"auto"`**: the candidate is `4380 + (parseInt(cfg.id, 16) % 100)`. `cfg.id` is six hex from
  `projectId` (24 bits, safely inside a JS number), so no new hash is introduced and the whole rule
  is one line. Probe upward from the candidate, at most 100 attempts, then fail with a message
  naming `monitor.port` as the way out. A project keeps its URL across restarts because the
  candidate is a pure function of its path.
- **A number** pins it. A pinned port that is taken **fails** — it does not probe upward. Someone
  who chose a stable URL is not served by being silently moved off it.
- **The port recorded in the registry is the one actually bound**, never the candidate. A project
  that had to probe past a collision is findable only if the recorded number is the true one; that
  is the entire reason §8.3 says so.

### 4. `doctor` reports a stolen pin as an error, not a warning (§8.3)

`orchestra doctor` gains one check: a pinned `monitor.port` that another **live** registered
instance holds prints an `error:` line naming the other project and its root, and sets exit code 1.
Not a warning — a warning here reads as "your page moved", and it did not: it will refuse to start.
This is the first thing in `doctor` that reads the machine registry and the first that can exit
non-zero; both are deliberate, and both belong here rather than in P5, because the pin is this
phase's key. An `"auto"` port is never in conflict by construction and prints nothing.

### 5. The registry becomes multi-writer, and that is a real defect to fix first

`lib/cli/tick.mjs` comments that `ready` "is the ONE command that writes the registry, so the
machine file has exactly one writer per project". **P4 makes that false**, and `recordInstance`
replaces the whole entry:

- `ready` writes `{id, name, root, mode, workers, conductorSession, conductorPid, beatAt}`;
- the monitor knows `{id, name, root, mode, port, monitorPid}` and nothing about workers.

Written as they stand, each erases the other's fields. The dangerous direction is the monitor
erasing `workers`: another project then reads `undefined`, counts 0, and launches **more** — the
opposite of the safe direction `lib/machine.mjs`'s header promises ("too few launches, never too
many"). So:

- **`recordInstance` merges** the incoming entry into the existing one for that id instead of
  replacing it. Each writer sends only the fields it owns; both send `id`, `name`, `root`, `mode`
  identically. The existing round-trip test (`test/machine.test.mjs`, workers 2 then 4) stays green
  under a merge — merging differs only for a field the new entry omits.
- **A stale `workers` must not be pinned alive by a live page.** `updatedAt` currently doubles as
  "the conductor reported itself", which is what bounds a dead conductor's count to
  `SEEN_STALE_MS`. A monitor refreshing the entry breaks that coupling and would freeze a `-9`
  conductor's count for as long as the browser tab is open. So `recordInstance` stamps
  **`workersAt`** whenever the incoming entry carries `workers`, and `otherWorkers` counts an
  entry's workers only while `workersAt` is within `SEEN_STALE_MS`. An entry written before this
  change has no `workersAt`; fall back to `updatedAt`, which is exactly today's behaviour.
- **`isLive` does not learn about `monitorPid`.** A live page is not a live conductor, and making
  the page's pid a liveness leg would keep a project's entry — worker count included — for days.
  The monitor instead **refreshes its own entry on a timer** (every 5 minutes, `unref`'d), which
  keeps it listed under the rule that already exists.

### 6. The board is read in a child process, with a deadline

`lib/cli/roadmap.mjs`'s `cmdBoard` builds the board in-process, and the obvious move is to call
`reconcile` directly from the server. Do not.

Online, `store.list()` shells to `gh`, and `lib/store/github/gh.mjs`'s `execFileSync` carries **no
timeout**. This server is single-threaded: an unbounded wait becomes the whole page. Measured
2026-08-12 in planetCraft: `/api/model` never answered, the browser sat on a request that could not
fail, a freshly started monitor did the same, and it read as the tool being broken rather than as
GitHub being unreachable — for nine hours. Bounding one `gh` call would not bound a board that
makes several.

So the board is `execFileSync(process.execPath, [<bin/orchestra>, 'roadmap', 'board', '--json'],
{ cwd: root, timeout: 10_000 })`, and the reader keeps all three of the source's rules:

- **a failure is remembered for 60 s** and the last good board keeps being served, said plainly as
  stale. Retried on every model build, a GitHub outage leaves the page answering for one second in
  eleven, which is indistinguishable from the hang the timeout just fixed;
- **a success is cached for `SERVERS_TTL_MS`** (5 s). Measured 2026-08-13 in planetCraft, 8
  worktrees: a healthy board took 3.0 s against a page that polls every 2 s, requests overlapped,
  and hand-timed responses degraded 15 s, 29 s, 47 s until the server answered nothing at all;
- **a killed child reports a signal, not a sentence** — `e.code === 'ETIMEDOUT' || e.signal ===
  'SIGTERM'` is what turns `spawnSync node ETIMEDOUT` into a sentence about the network.

There is no "absent board" state here: `bin/orchestra` always exists beside this module. Offline
the child is a node start against local markdown — cheap, and the fixture suite exercises exactly
that path.

### 7. The page reaches a conductor; it never creates one

The source's `POST /api/answer` spawns `tools/orchestra/cron-tick.sh` when no conductor is beating,
with a retry loop for a held lock. **None of that is ported**, for one reason: there is no script
to spawn. The tick runner is phase 5's `install-heartbeat`, and a page that started a bare
`claude -p` would be re-committing the failure the source's own comment records — six conductor
identities in half an hour on 2026-08-13, two `merge_agent` runs twelve seconds apart on one
branch, three answers unread because the register kept naming a reader that had already died,
because delivering an answer had been wired to CREATE a conductor instead of to REACH the live one.

So `POST /api/answer` answers with exactly two outcomes, both facts:

- `awake` — `liveConductor(root)` says a beat under a minute old belongs to a pid that answers
  signal 0. That session's `orchestra watch-answers` loop hands it this answer within seconds;
- `no-conductor` — the answer is in the inbox and the next tick will read it. The page says that in
  a sentence rather than implying anything was started.

`spawnTick`, `retryWhenFree`, `lockHeld` and the two retry constants are not ported. When P5 lands
the heartbeat, whether the page may wake it is P5's question to answer.

### 8. The dev-server list probes the ports orchestra recorded, not a port band

The source sweeps `lsof` over 5170–5599 — Vite's neighbourhood — and then resolves each holder's
cwd with a second `lsof` per pid to match it against a worktree. Neither survives a portable
plugin: the band is one project's toolchain (spec §13's line), and a Rust or Python project's dev
server is nowhere near it.

What the page actually needs is "the server this row told me about, is it up". The register already
carries it: `reg.port` on a row and `item.port` on a pending item, written by the conductor. So
`listServers(ports)` takes the ports the register names, makes **one** `lsof -nP -iTCP:<list>
-sTCP:LISTEN -F pn` call, and reports which of them are listening. The `ok` flag stays and means
what it meant: `lsof` exits non-zero both when it finds nothing and when it is not installed, and
reporting the second as the first would have the page state, confidently, something it never
checked — measured, not assumed: nothing found throws with `status: 1`, an absent binary throws
with `status: null` and `code: 'ENOENT'`.

The cost is real and must be stated in the module: a dev server on a port no register row names is
invisible to the page. The conductor's own orphan sweep (the skill's dev-server section) is where
that question is answered, and it is a shell procedure, not this page's job.

### 9. One page per project

`orchestra monitor` in a project whose registry entry names a port with a live listener **prints
that URL and exits 0** rather than binding a second port. Two pages for one project are not wrong,
they are confusing, and the second one makes the recorded port flap between two numbers — which is
the one field §8.3 asks to be trustworthy. The test is the recorded `monitorPid` answering signal 0
**and** `lsof` seeing a listener on the recorded port; either alone can lie (a recycled pid, an
unrelated process on the port).

## What P4 does not do, and why — read this before you "restore" something

Each of these is in the source and is deliberately left behind. Every one will look like an
omission to a reader who knows the source, so each is named here with its argument, and **the
argument goes into the code as a comment where a reader would otherwise reach for it.**

1. **The tick spawn.** Scope answer 7.
2. **`readProse`, `paragraphAt` and the `locate.mjs` subprocess.** The source's board CLI returned
   line numbers for `**Why.**` and `**Acceptance.**`, so the monitor shelled out to a second tool
   to slice the paragraphs out of the roadmap text. This plugin's `parseRoadmap` already collects
   both as prose, `store.list()` returns them, and `reconcile` spreads them onto every row — so
   `board --json` carries `why` and `acceptance` and there is nothing to reconstruct. About forty
   lines and one whole failure mode go away. **Verify this on a fixture before deleting anything**:
   run `orchestra roadmap board --json` in a fixture with the standard roadmap and read the two
   fields off a row. Task 2 says so as a step.
3. **The 5170–5599 port band and the per-pid cwd resolution.** Scope answer 8.
4. **`--port` on the command line.** The port has one source of truth: the config, resolved by
   `lib/monitor/port.mjs`. A flag would be a second, and the first thing it would break is the
   registry's promise that the recorded port is where the page is. `--no-open` stays, because a
   headless start is a real need and a browser launch is not part of serving.
5. **`npm install` in `invokeCommand`'s launch lines.** The source's launch equipped a fresh
   worktree. `skills/orchestra/SKILL.md` step 8 already carries the portable ruling — "**Do not run
   a dependency install here**", a project that needs one says so in `briefExtra` — and the page's
   copyable command block must not contradict the protocol it exists to serve.
6. **`tools/orchestra/monitor/README.md`** (257 lines). Its load-bearing rules go where this
   repository puts arguments — in the module that would otherwise be "simplified" — and its
   user-facing half goes into `README.md` and the skill's page section. A second document
   describing the page would be a third place for the same facts to disagree.
7. **The `orchestra-inbox` hook.** Phase 5's. The page writing the inbox is what makes it worth
   writing; it is not this phase's to add, and no sentence here may claim it exists.

## Known divergences you will meet, and what to write

**Describe the code. Where the spec and the code disagree, the code is what a person will run.**

1. **`pendingId` lives in `lib/register/pending.mjs` while the rest of the source's `keys.mjs`
   lands in `lib/monitor/keys.mjs`.** P2a ported the one function the register needed. The split is
   correct — the id is the register's vocabulary, the ask's footer and its options are the page's —
   and the single import across that seam is the point: an id computed one way in the page and
   another way by whatever reads the inbox would deliver an answer to nothing.
2. **`.claude/orchestra/…` becomes `.orchestra/…` everywhere**, resolved through
   `orchestraDir(root)` and `imagesDir(root)`, never spelled as a literal. The image roots are the
   checkout, `.orchestra/images/` and the worker's worktree — the three the skill already promises
   in "A question about a picture must carry the picture", and the same directory `orchestra
   archive-images` sweeps.
3. **`invokeCommand`'s launch block must agree with the skill's step 8, word for word on the
   facts**: `git worktree add <cfg.worktrees>/<slug> -b <branch> <cfg.mainBranch>`, then
   `claude --bg -n orchestra-<cfg.id>-<task slug> --model <model> --dangerously-skip-permissions`.
   The task slug is the register row's own id, lowercased, every run of non-alphanumeric characters
   replaced by a single dash (`lod/C2` → `lod-c2`). This is one fact in two documents; the branch
   review reads both.
4. **The etag's clock bucket now carries the board as well as the dev servers.** `sourceStamp`
   mixes `Math.floor(now / SERVERS_TTL_MS)` into the stamp because no file's mtime moves when a
   server starts. Online, no local mtime moves when the board changes either, so that same bucket
   is what expires the etag — say so in the comment, because a reader will otherwise try to stat
   something that does not exist.
5. **`node --test test/*.test.mjs` is the whole suite and it has no watch mode, no coverage gate
   and no lint.** The per-task review and the branch review are the only filter over prose.
6. **A ported test that passes on its first run is a pin, not a proof.** The source's 173 tests are
   evidence about the source's code; re-running them here shows the port did not break composition.
   The RED/GREEN obligation in this plan applies only to behaviour this phase invents — the port
   allocation, the registry merge, the known-ports probe, the doctor check and the end-to-end
   acceptance. Say which is which in each task report.

## The acceptance

Spec §15's P4 row: **"two fixtures serve at once on different ports, each page naming its own
project; killing one and restarting it returns the same port."**

`test/p4-acceptance.test.mjs`, under a temporary `HOME` (§14) so the registry under test is never
the developer's own, and driven through `bin/orchestra` wherever a subcommand exists.

**Split deliberately in two, and say why in the file's header.** What is served is asserted
**in-process**, by calling `createHandler(ctx)` and handing it a fake request/response — the shape
the source's own suite used. What needs two real listeners is asserted **out-of-process**, with two
`orchestra monitor --no-open` children. The seam between them is not timidity about sockets: an
in-process handler test is deterministic and fast, and this repository has a measured reason to
distrust an HTTP client against localhost as a *probe* (scope answer 2). If `fetch` against a
fixture's own child works on the implementer's machine, an extra round-trip assertion is welcome —
**the acceptance must not depend on it.**

| # | Assertion | Task |
|---|---|---|
| 1 | two fixtures, two ids, two different deterministic candidates; both children bind, both print their URL, and `~/.orchestra/instances.json` records each project's **bound** port | 4 |
| 2 | each page names its own project: `/` carries the project name in its `<title>`, and `/api/model`'s `project` block carries `name`, `root`, `mode` and the branch — asserted in-process, per fixture | 4 |
| 3 | killing one child and restarting it returns the **same** port | 4 |
| 4 | a project whose candidate is already taken probes upward, and the registry records the port it actually bound, not the candidate | 4 |
| 5 | `POST /api/answer` appends one line to `.orchestra/inbox.jsonl`, and `orchestra inbox` then prints that answer — the first time anything in this plugin writes that file | 4 |
| 6 | `orchestra instances` lists both projects with their names, roots, modes and ports, and says which is listening | 4 |
| 7 | a pinned `monitor.port` held by another live registered instance makes `orchestra doctor` print an `error:` line and exit 1 | 1 |
| 8 | `orchestra monitor` is silent and exits 0 with no config; `orchestra instances` answers anyway | 4 |

**Say this in the review rather than letting it pass for more than it is:** the suite proves the
page composes, allocates and round-trips an answer. It proves nothing about what the page *looks
like*, and nothing about the browser half beyond the bytes being served — no test here loads
`app.js`. That is the same limit the source's suite had, and it is why the pure modules the page
imports (`layout`, `progress`, `tabs`, `answers`, `clock`) are served to the browser rather than
duplicated in it: they are the half a test can reach.

### Task 1: the registry becomes multi-writer, and a project gets a port

**Files:**
- Modify: `lib/machine.mjs`, `lib/cli/doctor.mjs`
- Create: `lib/monitor/port.mjs`
- Test: `test/machine.test.mjs` (extend), `test/monitor-port.test.mjs` (new), `test/cli.test.mjs` (extend, for doctor)

**Interfaces:**
- Consumes: `projectId`, `loadConfigOrThrow` (`cfg.id`, `cfg.monitor.port`, `cfg.name`, `cfg.root`).
- Produces:
  - `recordInstance(entry, { now, alive })` — unchanged signature, **merging** semantics.
  - `otherWorkers(id, { now, alive })` — unchanged signature, now ignoring a stale `workersAt`.
  - `liveInstances({ now, alive })` → the live entries, for `orchestra instances` and `doctor`.
  - `candidatePort(id)` → `number` — `4380 + (parseInt(id, 16) % 100)`.
  - `listenOnFreePort(server, { port, pinned, host = '127.0.0.1', tries = 100 })` → `Promise<number>`

  - `pinConflict(cfg, instances)` → `null | { name, root, port }` — a pinned port held by another
    live instance.

**Why this is first.** Every later task writes the registry or reads a port, and this is the only
task in the phase whose defects are silent: a replaced entry loses a field nobody notices until a
fourth project over-launches, and a port probe that closes a socket before the real bind fails once
in a hundred starts.

  passes against today's code:

- [ ] **Step 2: implement.** Merge in `recordInstance`; stamp `workersAt` only when `workers` is

5. **`lib/register/archive.mjs`'s drop path silently disarms the heartbeat override, and the comment

   stand-down gate honours an open question on any row *whatever that row's status*. That holds on one
   of the two paths only: a terminal row something still depends on is kept as a stripped tombstone and
