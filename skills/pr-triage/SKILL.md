# PR triage

You are triaging a pull request for the maintainer. They decide, you prepare.

**Nothing here names a repository, a path or a module.** This skill is installed into projects it
has never heard of, so the three facts it needs are read at the start of every run:

```sh
"${CLAUDE_PLUGIN_ROOT}/bin/orchestra" doctor      # `root`, `pr.direction`, `briefExtra`
REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)
```

- **`$REPO`** is what every `gh api` call below means by `OWNER/REPO`. Never type a repository name.
- **`pr.direction`** is the directory holding this project's direction memory. Resolve it against
  `doctor`'s own `root` row, **never against the directory you are standing in**: a review runs in a
  worktree that is deleted when the row ends, and a principle written there dies with it.
- **`briefExtra`** is where the project states the rules a prompt cannot derive. It is half of the
  blast radius in step 2, and the project's own `CLAUDE.md` is the other half.

From here on `orchestra <subcommand>` means `"${CLAUDE_PLUGIN_ROOT}/bin/orchestra" <subcommand>`,
and `bin/orchestra` at the root of the plugin's own directory when `CLAUDE_PLUGIN_ROOT` is unset.

## Hard rules

These are not preferences. Breaking one is a failure of the task.

1. **Never publish anything on GitHub.** No `gh pr comment`, no `gh pr review --approve
   / --request-changes / --comment`, no `event` field in the reviews API, no merge, no
   close, no label, no assignee. The only write you may perform is creating a **pending**
   review, which is private to the maintainer. Everything else needs their explicit
   spoken go, per request.
2. **Never merge and never close.** Even on a MERGE verdict. The maintainer clicks it.
3. **No `—` character** in anything destined for GitHub or for the maintainer to paste.
   Use a comma, a colon, parentheses, or a new sentence.
4. **No signature, no co-author trailer, no "generated by" line.** Ever. Not in the
   review body, not in inline comments, not in the paste-ready text.
5. **Verify before you claim.** Never report the draft as ready without running the
   verification in `reference/pending-review.md` step 4.

Orchestra having a merge gate does not soften rule 1 or rule 2. `orchestra land` is for branches
this project owns; a pull request is somebody else's branch, and the gate is never run on one.

## Step 0: load direction

Read `<pr.direction>/DIRECTION.md` and every file it indexes, before you look at
the PR. Prior calls constrain this one. If the folder is missing or empty, note that
and continue: the direction memory is built by this skill over time.

## Step 1: gather

```bash
gh pr view N --json title,body,author,state,isDraft,baseRefName,headRefName,\
additions,deletions,changedFiles,files,labels,mergeable,createdAt
gh pr diff N
gh pr checks N
gh api "repos/$REPO/pulls/N/reviews" -q '.[] | "\(.state) by \(.user.login)"'
gh api "repos/$REPO/issues/N/comments" -q '.[] | "[\(.user.login)] \(.body[0:200])"'
```

Also check whether the PR links or should link an issue. Search open issues for the
problem it claims to solve. A net-new untracked feature is worth flagging.

If the diff is very large, spawn `Explore` subagents over slices of it rather than
reading everything inline, but read every hunk that touches the project's own source
yourself — the source directories are what `CLAUDE.md` and `briefExtra` name.

## Step 2: explain it in plain words

Before any verdict, write for the maintainer:

- **The problem it says it solves.** One or two sentences, their words translated to plain.
- **What it actually changes.** The real mechanism, not the PR title. If the body and
  the diff disagree, say so, that is a finding.
- **Blast radius.** Which features can break. **You do not know this project by heart, so read it
  rather than guess**: `briefExtra` from `orchestra doctor` states the rules a prompt cannot derive,
  and the project's own `CLAUDE.md` states its architecture — which module is shared, which state is
  global, which file everything imports. Name the blast radius from those two, by module. If neither
  says anything about the files this PR touches, say that plainly instead of inventing a coupling:
  "the project documents no shared state covering these files" is itself a finding, both about the
  PR and about the project.
- **Size and shape.** Focused fix, or a dump of unrelated work in one branch.

Plain language means no jargon the maintainer has to decode. Short.

## Step 3: verify the claims

Do not trust the PR body. This step is what makes the triage worth anything.

- **Check what the PR emits against the version this project actually pins.** A CLI flag, a config
  field or an import the PR adds must exist at the version in the project's own manifest — a
  `package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`, a lockfile, a pinned git tag. Read the
  installed dependency, not the upstream documentation: the pin is what runs, and the docs describe
  a later release more often than not.
- **Read the contributor's actual files, not just the diff**, when a hunk depends on
  surrounding code:
  ```bash
  SHA=$(gh pr view N --json headRefOid -q .headRefOid)
  FORK=$(gh pr view N --json headRepositoryOwner -q .headRepositoryOwner.login)
  gh api "repos/$FORK/${REPO#*/}/contents/PATH?ref=$SHA" -q .content | base64 -d
  ```
  `${REPO#*/}` is the repository's own name with the owner stripped; the fork keeps that name.
- **Check the conventions the PR may be violating**, from the project's `CLAUDE.md` and from
  `briefExtra`: where shared paths must come from, which helper a feature has to call before it does
  anything, which vocabulary must not be conflated with which. Cite the rule by name and by line, so
  the maintainer can disagree with the rule rather than with you.
- **Generated or built artifacts committed into the diff.** If CI rebuilds it, committing it bloats
  the diff and invites conflicts. Read the workflows before claiming it: a project that ships its
  build output on purpose is not making a mistake, and saying so wrongly costs a contributor's trust.
- **CI state.** Green, red, or never ran.

State plainly which claims you verified and which you could not.

## Step 4: verdict

Pick exactly one.

**MERGE**: correct, in direction, contained, CI green, nothing worth blocking on.
Small nits alone do not downgrade this.

**REVIEW**: worth engaging, but something needs to change or be answered first. Real
correctness problems, missing tests on a load-bearing helper, convention violations,
unclear intent.

**DECLINE**: you would not take this. Two flavours, both DECLINE, both write direction:
- *wrong direction*: scope, architecture, or a feature that does not belong.
- *not worth the time*: stale, duplicate, unfocused dump, superseded.

Justify the verdict against the direction files by name when one applies.

## Step 5: act

### MERGE

Nothing on GitHub. Give the maintainer a short approval note to paste, and say plainly
that they merge it themselves.

### REVIEW

Draft a **pending** review. Follow `reference/pending-review.md` exactly, including the
verification in its step 4.

- Inline comments: one per concrete, actionable finding, anchored to the line it is
  about. Say what is wrong and what to do. Skip pure formatting nits.
- Review body: what you verified and it held up (contributors deserve to know their
  work was actually read), then the two or three things that matter most before merge,
  then anything structural like a missing linked issue.
- Then give the maintainer a **separate short warm comment to paste** as the public
  overall note. Thankful, specific about what is good, honest about what is needed.
  Short. No `—`. Never post it.

### DECLINE

Nothing on GitHub.

1. Work out the durable rule behind the call. Not the PR story, the reusable principle.
   "This PR bundles a rebuilt bundle directory" is a story. "PRs must not commit the built
   bundle, CI rebuilds it on the main branch" is a principle.
2. If an existing file in `<pr.direction>/` already covers it, append the PR number
   as another evidence line instead of creating a new file.
3. Otherwise write `<pr.direction>/<kebab-slug>.md` in the format below, and add one
   index line to `<pr.direction>/DIRECTION.md`.
4. Give the maintainer a short warm decline note to paste when they close it. Thankful,
   states the direction reason, no blame.

**Never write a direction principle the maintainer did not state.** A principle you reasoned out
yourself from a decline you also reasoned out yourself is legitimate — that is this step. A
principle invented to justify a call you are unsure of is not, and it poisons every later sweep,
because the next one will cite it as settled. If you cannot state an honest rule from what you read,
say so and ask.

Direction file format:

```markdown
# <Principle, stated as a rule>

<Two or three sentences: the rule, and why the project holds it.>

## Evidence
- PR #64: bundled a rebuilt bundle directory, 1.4MB of diff noise.
```

## Step 6: record the verdict

One line, through the command, before you stop:

```sh
orchestra pr log <N> <review|merge|decline|dismissed> --head <sha> [--comment <id>] \
  [--note "one short line, why"] [--direction <file.md>]
```

- **`dismissed`, not `dismiss`.** The record says what happened, and the four words above are the
  only ones the command accepts: an unknown verdict is refused rather than written.
- **`--head` is the sha you ACTUALLY reviewed**, not a fresh fetch. It is half the watermark that
  lets the next sweep tell a PR that moved from twenty that did not, so a record with no head is
  refused. When a sweep handed you a head and a comment id, use those.
- **`--comment` is the highest comment id from anybody but the maintainer** at the time you looked,
  the other half of that watermark. A sweep gives it to you; omit it if nobody has.
- **`--direction`** is the direction filename that justifies a `decline`.
- **Never `printf` a line into the ledger by hand.** The command takes the clock itself, refuses an
  unknown verdict, writes one complete line per append and repairs a missing trailing newline
  before the next one. Review workers append concurrently, so a read-modify-write, or a hand-built
  line, loses records — `lib/pr/ledger.mjs`'s own header says why.
- It resolves the ledger against the **main checkout**, so it is correct run from inside a review
  worktree.

## Output to the maintainer

In this order, tight:

1. **What this PR does** (plain words)
2. **What I verified** (held up / did not hold up / could not check)
3. **Verdict** and why, citing direction files by name where they apply
4. **What I did**: pending review URL, or direction file written, or nothing
5. **Paste-ready comment** in a fenced block, short

Keep the whole thing scannable. The maintainer reads a lot of these.

**If you are a review worker a conductor launched**, that output is your FINAL MESSAGE and your
session ends with it — replying to the conductor's address does not work, which your brief already
told you. The ledger line in step 6 must already be written before you stop, and if the row ships
something the maintainer will want to try, start the project's own dev server first and report the
port it ACTUALLY bound plus its pid: they test the PR themselves at the hands-on gate.
